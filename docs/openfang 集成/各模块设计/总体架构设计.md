# OpenFang 集成总体架构设计

## 1. 这份文档要解决什么问题

`开始文档.md` 的问题不在方向，而在粒度。

它把第一阶段切成了一个很小的业务闭环，适合验证，但不适合作为后续几年持续扩展的底座。

如果现在不先把总体边界、公共中间件职责、技术选型和模块分层钉死，后面每加一个场景都会重复做下面这些事情：

- 重写一套场景专用 Tool
- 重写一套场景专用权限校验
- 重写一套场景专用上下文拼装
- 重写一套场景专用审批接入
- 重写一套场景专用审计链路

这样会很快把系统拖成“很多能跑的小功能”，但没有一个真正的平台。

这份文档的目标是把 OpenFang 与 OA 集成，从“单场景接入”升级成“平台级架构设计”。

## 2. 总体判断

结论先写清楚：

- 必须同时做自上而下和自底向上的设计
- 中间件不能按单场景定制，必须先抽成平台公共层
- 主体技术选型建议是：`Java 为主，Rust 为辅`
- 近期不建议把中间件主实现押在 Rust 上
- 建议把系统拆成 `治理面`、`集成面`、`运行面`、`场景面`

一句话总结：

```text
OA 负责治理真相
OpenFang 负责 Agent Runtime
集成中间件负责把“治理约束”翻译成“可运行能力”
场景模块只负责装配，不负责重造基础设施
```

## 3. 技术选型结论

## 3.1 为什么主选 Java

当前仓库本身就是 Java 主体系统，且现状非常关键：

- 主工程是 Maven 多模块
- 当前运行基础是 Spring Boot 2.7.x
- 项目基线仍然兼容 JDK 8
- 现有 BPM、System、ERP、AI 模块都在 Java 体系内

这意味着如果中间件主实现改用 Rust，马上会出现 4 个成本：

- 组织模型、权限模型、BPM 接口要跨语言重建
- 发布、运维、日志、鉴权、配置中心要多一套
- 开发团队需要同时维护 Java 和 Rust 两套核心业务代码
- 后续大部分业务场景接入都要跨进程、跨协议、跨调试链路

对当前阶段来说，这些成本远大于收益。

所以主结论是：

- `集成中间件主实现选 Java`
- `优先作为 yudao 内一个独立模块落地`
- `先和 BPM / System / AI 模块跑通同进程能力，再决定是否拆服务`

## 3.2 Rust 适合放在哪

Rust 不是不能用，但不应该成为第一阶段主技术栈。

Rust 更适合后续承担这些位置：

- 高并发 Tool Gateway
- 安全隔离要求更高的执行代理
- 沙箱执行器
- 流式协议网关
- 高吞吐事件采集或审计代理

也就是说，Rust 适合做“高性能边缘部件”，不适合现在直接承担“组织、权限、审批、场景编排”这类强业务耦合的中间层。

## 3.3 最终建议

建议采用下面的技术策略：

```text
Phase 1:
Java = 平台主实现
Rust = 不引入核心链路

Phase 2:
Java = 治理面 + 场景编排 + 业务接入
Rust = 沙箱执行器 / 高性能网关 / 特定 Tool 代理
```

这比“现在就全押 Rust”稳得多，也比“什么都塞进 Java 单体”更有演进空间。

## 4. 自上而下的总体设计

先从顶层看，不从请假流程看。

未来不管做审批助理、CRM 助理、知识助理、采购助理，本质上都在做同一件事：

```text
把企业治理体系中的身份、权限、流程、数据、审计
转成 OpenFang 可运行的 Agent 能力
```

所以顶层必须拆成四层。

### 4.1 治理面

由 OA 负责，是真相源。

职责：

- 组织架构
- 人员与岗位
- 角色与数据权限
- BPM 审批
- 业务单据
- 企业主数据
- 审计归档

不负责：

- Agent Runtime 状态机
- Tool 执行编排
- 多 Agent 协作

### 4.2 集成面

这是本次必须重点建设的中间件层。

职责：

- 身份映射
- 权限映射
- Tool 能力注册
- 任务投递
- 上下文组装
- 审批绑定
- 事件回流
- 审计标准化
- 场景编排

这层不是一个 Controller 集合，而是平台公共层。

### 4.3 运行面

由 OpenFang 负责。

职责：

- Agent 定义
- Skill 装配
- TaskRun 执行
- Workspace Context
- 多轮决策
- Tool 调用
- 中断、恢复、失败重试
- 运行时审批阻塞

### 4.4 场景面

每个业务场景只做最薄的一层装配。

例如：

- 请假审批助理
- 报销审批助理
- CRM 客户分析助理
- 周报分析助理
- ERP 采购建议助理

场景面应该依赖公共平台，不应该反过来定义平台。

## 5. 自底向上的能力抽象

如果从底层往上看，平台必须先把公共能力抽象出来，否则所有场景都会重复造轮子。

建议把公共能力固定成 8 类。

### 5.1 Identity

回答“谁在执行”。

核心对象：

- `HumanPrincipal`
- `AgentPrincipal`
- `DelegationContext`
- `OnBehalfOfContext`

规则：

- Agent 不是 OA 普通用户
- Agent 必须有独立安全主体
- 代理执行必须显式带上委托上下文

### 5.2 Authorization

回答“能做什么”。

核心对象：

- `Capability`
- `ToolPermission`
- `DataScope`
- `ApprovalPolicy`

核心原则：

- 权限不是复制 OA 菜单权限
- 权限是“可执行能力”
- 实际权限 = Agent 能力 ∩ 用户委托范围 ∩ 场景策略

### 5.3 Tool Registry

回答“有哪些工具可用”。

核心对象：

- `ToolDescriptor`
- `ToolSchema`
- `ToolPolicy`
- `ToolAdapter`

规则：

- Tool 不直接暴露业务表
- Tool 面向受控服务能力，不面向数据库
- Tool 必须带输入输出 schema、风险等级、审计标签

### 5.4 Context Assembly

回答“运行时上下文怎么形成”。

核心对象：

- `ContextProvider`
- `ContextSnapshot`
- `BusinessContextBundle`

作用：

- 把 BPM、业务单据、用户资料、组织信息、知识摘要统一拼装
- 屏蔽下游场景对多个模块的直接依赖

### 5.5 Task Orchestration

回答“任务怎么创建、执行、终止、补偿”。

核心对象：

- `TaskRequest`
- `TaskBinding`
- `TaskProjection`
- `TaskEvent`

注意：

- TaskRun 真相在 OpenFang
- OA 只保存投影和关联，不接管 OpenFang 内部状态机

### 5.6 Approval Bridge

回答“审批怎么和 Agent Runtime 对齐”。

核心对象：

- `ApprovalRequest`
- `ApprovalBinding`
- `ApprovalDecision`

原则：

- 审批真相只在 OA BPM
- OpenFang 只能发起审批需求和接收结果
- 不能双边各保一套审批状态机

### 5.7 Audit & Observability

回答“出了问题怎么追”。

核心对象：

- `AuditRecord`
- `ToolInvocationLog`
- `PromptTrace`
- `DecisionTrace`
- `BusinessActionLog`

必须保证：

- 谁发起
- 谁代理
- 调了什么 Tool
- 读了什么数据域
- 触发了什么审批
- 最终写了什么业务动作

### 5.8 Scenario Kit

回答“场景如何快速接入”。

核心对象：

- `ScenarioDefinition`
- `ScenarioContextProvider`
- `ScenarioToolSet`
- `ScenarioPolicy`

目标：

- 新场景开发只需装配，不需重造基础模块

## 6. 平台模块划分

建议在 OA 侧新增独立平台模块，名字可以叫：

- `yudao-module-agentx`
- 或 `yudao-module-openfang`

不建议继续用“某个单一场景模块名”。

建议拆成下面 10 个子模块，哪怕第一阶段可以先做成一个 Maven module 内的多个 package，也要按这个边界设计。

### 6.1 `agentx-domain`

职责：

- 定义平台核心领域对象
- 定义状态枚举
- 定义公共协议对象

包含：

- principal
- capability
- task binding
- approval binding
- audit record

### 6.2 `agentx-identity`

职责：

- Agent 身份建模
- 人与 Agent 的委托关系管理
- On-Behalf-Of 上下文生成

### 6.3 `agentx-authorization`

职责：

- 能力授权
- Tool 权限控制
- 数据域控制
- 场景策略评估

### 6.4 `agentx-tool-registry`

职责：

- Tool 元数据注册
- Tool 适配器装配
- Tool 风险等级声明
- Tool schema 管理

### 6.5 `agentx-context`

职责：

- 跨 BPM / System / ERP / CRM 的业务上下文组装
- 形成统一 `BusinessContextBundle`

### 6.6 `agentx-runtime-bridge`

职责：

- 调用 OpenFang Runtime
- 创建 TaskRun
- 查询运行状态
- 接收回调事件

这是 OA 与 OpenFang 的协议边界。

### 6.7 `agentx-approval-bridge`

职责：

- 将高风险动作映射到 OA BPM
- 维护审批绑定关系
- 把审批结果回推 OpenFang

### 6.8 `agentx-audit`

职责：

- 审计日志标准化
- Tool 调用留痕
- Prompt / 决策轨迹归档
- 风险事件留痕

### 6.9 `agentx-scenario`

职责：

- 放各类业务场景的装配代码
- 例如 leave、expense、crm、erp、knowledge

这里不做公共基础设施。

### 6.10 `agentx-console`

职责：

- 提供配置和运营 UI
- 例如 Agent 配置、授权范围、任务绑定、审批查看、审计查询

## 7. OpenFang 与 OA 的协议边界

这个边界必须先钉死，否则后面必乱。

## 7.1 OA 可以知道什么

- TaskRun 外部 ID
- 当前状态投影
- 风险等级
- 待审批动作
- 最终结果摘要
- Tool 调用审计摘要

## 7.2 OA 不应该知道什么

- OpenFang 内部 prompt 编排细节
- 内部 agent loop 状态实现
- 内部 memory 结构细节
- 具体推理链实现

## 7.3 OpenFang 可以直接访问什么

- 只能访问集成面暴露的受控工具和接口

## 7.4 OpenFang 不能直接访问什么

- OA 数据库表
- 未注册的内部服务
- 绕过审批的写接口

## 8. 请求链路总图

建议统一成下面这条链，不要按场景各搞一套：

1. 用户从 OA 页面、IM 或 API 发起任务
2. OA 将请求转成 `ScenarioTaskRequest`
3. `agentx-context` 组装业务上下文
4. `agentx-authorization` 计算当前能力边界
5. `agentx-runtime-bridge` 调用 OpenFang 创建 TaskRun
6. OpenFang 按 Skill 和 Tool 执行任务
7. 涉及高风险写操作时，OpenFang 通过 `agentx-approval-bridge` 发起审批
8. OA BPM 完成审批
9. 审批结果回流 OpenFang
10. OpenFang 继续执行或终止
11. 结果和轨迹通过 `agentx-audit`、`agentx-console` 回投 OA

这样无论是请假、报销还是 CRM，主链路都不变。

## 9. 为什么中间件必须做成“平台公共层”

因为真正会被重复使用的不是“请假审批逻辑”，而是下面这些骨架：

- 统一身份映射
- 统一委托执行
- 统一 Tool 注册
- 统一上下文拼装
- 统一审批桥接
- 统一审计
- 统一任务绑定

如果这些不抽出来，后面每个场景都会内嵌一份自己的：

- 身份判断
- BPM 读写逻辑
- 审批回调逻辑
- Tool 白名单
- 审计留痕格式

最终结果就是：

- 代码重复
- 安全边界不一致
- 审计口径不一致
- 场景越多，维护越慢

## 10. 场景层应该怎么做

场景层只做四件事：

- 定义场景入口
- 声明需要的上下文
- 声明需要的 Tool 集
- 声明该场景的风险和审批策略

例如请假审批场景，不应该自己持有一套完整中间件，而应该只是：

- `LeaveScenarioDefinition`
- `LeaveContextProvider`
- `LeaveToolSet`
- `LeaveApprovalPolicy`

后续新增报销审批，只是换成：

- `ExpenseScenarioDefinition`
- `ExpenseContextProvider`
- `ExpenseToolSet`
- `ExpenseApprovalPolicy`

中间层骨架完全复用。

## 12. 部署形态建议

第一阶段不要上来拆很多独立服务。

建议形态：

```text
OA 单体/模块化应用
  ├─ BPM
  ├─ System
  ├─ ERP/CRM/...
  └─ AgentX 集成模块

OpenFang Runtime
  └─ 独立运行
```

也就是：

- OA 内新增 `AgentX` 集成模块
- OpenFang 保持独立运行时
- 二者通过明确 API/事件协议交互

这样做的优点：

- 先利用现有 Java 系统能力
- 先把模型边界跑顺
- 不急着把复杂度转成分布式复杂度

## 13. 分阶段实施建议

## 13.1 Phase 0：先钉边界

本阶段输出：

- 核心对象模型
- 模块边界
- 协议边界
- 权限模型
- 审批模型

不急着做很多场景。

## 13.2 Phase 1：做平台骨架

优先落地：

- identity
- authorization
- tool registry
- context assembly
- runtime bridge
- approval bridge
- audit

这一步完成后，平台才算成型。

## 13.3 Phase 2：接入第一个场景

第一个场景仍然可以是：

- `请假审批助理`

但它此时只是平台上的第一个插件，而不是整个平台本身。

## 13.4 Phase 3：扩展同类场景

优先扩展：

- 报销审批
- 出差审批
- 采购申请审批

这些场景最容易复用审批桥接和上下文拼装能力。

## 13.5 Phase 4：扩展到经营类场景

例如：

- CRM 跟进总结
- ERP 采购建议
- 周报经营分析

到这一步，平台公共层的价值才会被真正放大。

## 14. 明确的反模式

下面这些设计现在就应该禁止：

- 为每个场景各写一套“专用中间件”
- 让 OpenFang 直接查 OA 数据库
- 让 Agent 冒充 OA 用户直接执行所有接口
- 审批在 OA 做一份、OpenFang 再做一份
- Tool 直接绑定表结构而不是服务能力
- 场景代码里直接硬编码权限判断

这些设计短期快，长期一定拖死扩展速度。

## 15. 最终结论

这次重新规划后，方向应该明确成下面这句话：

```text
不是先做一个请假审批 Agent，
而是先做一个可承载审批、分析、知识、经营类 Agent 的统一集成平台，
请假审批只是第一个落地场景。
```

技术上：

- 主技术栈选 `Java`
- 短期不把核心中间件押在 Rust
- Rust 作为后续高性能执行代理或网关的补充选项

架构上：

- 自上而下先钉治理面、集成面、运行面、场景面
- 自底向上先建设 identity、authorization、tool registry、context、approval、audit 等公共骨架
- 场景层只做装配，不再定义平台边界

如果后续要继续细化，下一份文档建议直接拆成：

- `01-核心对象设计.md`
- `02-权限与委托模型.md`
- `03-Tool 注册与协议设计.md`
- `04-审批桥接设计.md`
- `05-场景接入规范.md`

这样后面写代码时，模块边界就不会再反复摇摆。
