 不要把 OpenFang 硬塞进 OA，当成 OA 里的一个“大功能模块”。
  也不要让 OA 去主导 Agent runtime。
  正确做法是：

  OA = 企业组织与治理真相源
  OpenFang = Agent 执行内核
  集成层 = 授权、任务、审批、审计、知识同步

  原因很简单。
  OA 擅长的是组织、权限、流程、审计、业务对象。
  OpenFang 擅长的是 Agent、channel、skill、task runtime、approval gate、工具执行。
  这两套系统都想当老大，就一定烂掉。

  从仓库看，OpenFang 自己已经在往这个方向走了，不需要你重新发明概念：

  - 它已经把自己定义成 Agent OS，而不是聊天框架，见 README.md:36 和 README.md:231。
  - 它已经有“企业组织 → 部门 → Agent 员工 → 工具”的权限模型草图，见 README.md:7。
  - 它已经明确了双权限链 入口权限 ∩ 工具权限，这正是企业集成的关键，见 README.md:15。
  - 它已经把 TaskRun 做成一等公民，这说明它知道长任务、打断、审批、副作用都不能靠聊天记录硬撑，见 README.md:15。
  - 更关键的是，OpenFang 仓库里已经有“数字部门”设计文档，而且方向基本是对的，见 2026-03-09-群聊式数字部门与-agent-skill-执行模型.md。

  所以你现在不是从 0 到 1。你现在的问题是：把这个想法从“产品叙事”收敛成“系统边界”。

  我的判断
  “在 OA 里设一个 AI 部门，然后把 OpenFang 的 Agent 当数字员工”这个抽象是成立的，但只能成立一半。

  成立的部分：

  - 部门
  - 岗位
  - 员工
  - 汇报关系
  - 审批链
  - 数据权限
  - 任务分发

  这些都可以映射。

  不成立的部分：

  - 不要把 Agent 真的当成 OA 用户的一个普通变体
  - 不要让 Agent 直接继承 OA 全部行为语义
  - 不要让 OA 成为 Agent runtime 的编排器

  因为 Agent 不是“会自动工作的普通员工账号”，它是带 runtime、memory、tool sandbox、approval gate 的执行体。这个部分只能在 OpenFang 里成立。

  所以我建议你把“AI 部门”改成两个概念：

  1. 数字组织视图
     给 OA 用户看的。
     部门、岗位、AI 员工、主管、任务、待办、审批、绩效。
  2. Agent Runtime 视图
     给 OpenFang 用的。
     department profile、role agent、skill bundle、knowledge pack、task run、approval request、workspace session。

  前者是业务建模，后者是执行建模。
  名字可以像，但不要用同一套表硬扛。

  最重要的设计原则
  只有一个真相源负责一类问题。

  建议这样分：

  - OA 负责：
      - 组织架构
      - 人员/岗位
      - 角色权限
      - BPM 审批
      - 业务单据
      - 企业知识主数据
      - 审计归档与报表
  - OpenFang 负责：
      - Agent 定义与运行
      - Skill / Tool 执行
      - 多 Agent 协作
      - Channel 接入
      - 会话与 workspace context
      - TaskRun 状态机
      - Approval gate 的运行时阻塞
  - 集成层负责：
      - 身份映射
      - 能力映射
      - 任务投递
      - 审批回调
      - 事件同步
      - 只读知识同步 / 检索代理

  如果你把审批同时做在 OA 和 OpenFang 里，最终一定出现“双审批真相”。这必须避开。

  我建议的核心模型
  先别上代码，先把这 8 个对象钉死：

  - OrgUnit
    OA 的真实部门。比如销售部、采购部、法务部。
  - DigitalDepartment
    一个面向 Agent 协作的业务视图。可以映射到一个或多个 OA 部门。
    这是给 OpenFang 和 UI 用的，不必等于 OA 的行政部门。
  - RoleAgent
    数字岗位实例。比如 sales_assistant_agent、approval_secretary_agent、crm_analyst_agent。
  - AgentPrincipal
    Agent 的安全主体。它不是 OA 用户，但要有可审计身份、签名、能力边界。
  - KnowledgePack
    该岗位可读的知识域，不是全库可见。
  - ToolCapability
    Agent 可调用的企业工具集合，不是权限字符串的简单复制。
  - TaskRun
    一次具体任务执行，唯一真相在 OpenFang。
  - ApprovalBinding
    OpenFang 的审批节点与 OA BPM 实例的绑定关系。

  这几个对象里，最容易被做错的是 AgentPrincipal。
  如果你直接让 Agent 冒充 OA 普通用户去调接口，后面权限、审计、撤权、离职、风控都会出事故。

  正确做法是：

  - Agent 有独立 principal
  - 当它“代表某人”执行时，进入 On-Behalf-Of 模式
  - 权限取交集，而不是直接继承用户权限

  这正好和 OpenFang 文档一致，见 README.md:33。

  一条正确的请求链路
  我给你一个最务实的链路，不玩虚的。

  1. 用户在 OA 或飞书里发起请求
  2. 请求进入 OA，形成业务任务或协作任务
  3. OA 判断是否交给某个 DigitalDepartment
  4. 集成层调用 OpenFang，创建 TaskRun
  5. OpenFang 根据角色、skill、workspace context 执行
  6. 涉及企业动作时，调用 Tool Gateway
  7. Tool Gateway 不直接写 OA 数据，而是走受控企业 API
  8. 高风险动作生成审批
  9. 审批真相落在 OA BPM
  10. OA 把审批结果回推 OpenFang
  11. OpenFang 继续 / 终止 / 补偿
  12. 全链路事件回写 OA 做审计和经营视图

  注意两个原则：

  - 任务真相 在 OpenFang
  - 审批真相 在 OA

  这就是边界。

  你现在最不该做的 5 件事

  - 不要把 Agent 直接建成 OA 用户表里的一种用户类型，然后共享全部登录/菜单/会话逻辑。
  - 不要让 OpenFang 直接连 OA 数据库写表。
  - 不要让 OA 去理解 OpenFang 的内部状态机细节。
  - 不要把业务流程编排写死进 OpenFang 内核。
  - 不要一开始就追求“一个 AI 部门包打天下”。

  这些都是后期必炸的设计。

  最自然的第一阶段集成
  第一阶段不要做“AI 员工自治组织”，先做“OA 驱动的受控执行”。

  优先场景：

  - 审批助理
  - 知识问答助理
  - 销售助理
  - CRM 清洗助理
  - 周报分析助理

  统一模式：

  - Agent 只读多，写少
  - 写动作必须过审批或明确授权
  - 所有写动作走企业 API，不走 DB
  - 所有高风险动作可回滚或补偿

  这才是能上线的版本。

  产品壳怎么设计
  我不建议首页直接做“Agent 聊天大厅”。
  更合理的是两层 UI：

  - OA 侧：
      - 数字组织
      - AI 岗位配置
      - 授权范围
      - 待办与审批
      - 审计与绩效
  - OpenFang 侧：
      - TaskRun 详情
      - 工作空间上下文
      - Tool 调用轨迹
      - 失败分类
      - 运行时诊断

  业务用户看 OA。
  平台运营和研发看 OpenFang。
  不要逼业务用户理解 runtime。
