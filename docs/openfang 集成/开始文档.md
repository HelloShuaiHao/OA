# OpenFang 集成开始文档

## 1. 目的

这份文档不再讨论“AI 部门”这种大概念。

它只回答一个问题：

> 如果今天就要开工，第一刀应该做什么，OpenFang 需要什么，AgentHub 需要什么，OA 需要接哪个场景。

结论先写在前面：

- 第一版只做一个场景：`请假审批助理`
- 第一版只做一个 Agent：`leave_approval_copilot`
- 第一版只做一组固定 Tools，不做通用 Agent 平台
- 第一版只服务一个真实审批人处理一条真实待办

## 2. 为什么选这个场景

当前 OA 仓库里：

- BPM 引擎能力很完整
- 但明确落地的 OA 审批业务单据，目前只看到请假
- 对应数据对象已经存在：`BpmOALeaveDO`

因此第一版不应该做“通用审批助手”，而应该做：

`请假审批 AI 助理`

原因：

- 业务对象明确
- 审批动作明确
- 流程入口明确
- 风险范围可控

## 3. 自底向上的系统拆解

要开工，顺序必须是：

1. OpenFang 里定义什么 Agent
2. 这个 Agent 由哪些 Skills 组成
3. 每个 Skill 需要什么 Tools
4. Tools 连接到哪个系统
5. AgentHub 只做什么中间胶水
6. OA 最后接哪个页面和哪个动作

不要反过来。

## 4. OpenFang 第一版需要什么

### 4.1 Agent

只定义一个 Agent：

- `leave_approval_copilot`

职责：

- 读取请假审批上下文
- 生成摘要
- 识别风险
- 生成建议动作
- 在明确授权下执行标准审批动作

第一版不允许它：

- 自己发现任务
- 主动扫全站流程
- 跨流程乱跳
- 直接写 OA 数据库
- 处理复杂多 Agent 协作

### 4.2 Skills

第一版只要 3 个 Skills。

#### Skill 1：`leave-context-reader`

职责：

- 把 BPM 流程实例、流程任务、请假单、申请人信息整理成统一上下文

输入：

- `oa_user_id`
- `bpm_task_id`
- `process_instance_id`
- `leave_id`

输出：

- `leave_context`

#### Skill 2：`leave-risk-analyzer`

职责：

- 基于请假上下文识别异常和风险

第一版可做的风险项：

- 请假时长异常
- 请假时间与已有记录冲突
- 申请人近期请假过于频繁
- 部门关键岗位可能缺岗
- 表单字段不完整

输出：

- `risk_points[]`
- `risk_level`

#### Skill 3：`leave-action-advisor`

职责：

- 根据上下文和风险给出建议动作

第一版只允许输出：

- `approve`
- `reject`
- `return_for_more_info`

也就是：

- 建议通过
- 建议驳回
- 建议退回补充信息

第一版不要做复杂审批动作建议。

## 5. OpenFang 第一版需要什么 Tools

第一版只做 6 个 Tools。

这些 Tools 全部通过 AgentHub 暴露，不允许 OpenFang 直接调 OA Controller 或直接查库。

### 5.1 `get_leave_process_instance`

用途：

- 获取请假对应的流程实例信息

来源系统：

- OA 的 `yudao-module-bpm`

读取内容：

- 流程实例 ID
- 发起人
- 当前状态
- 当前审批节点

### 5.2 `get_leave_task_detail`

用途：

- 获取当前待办任务和历史审批记录

来源系统：

- OA 的 `yudao-module-bpm`

读取内容：

- 当前任务
- 当前候选人或处理人
- 历史审批意见
- 历史动作

### 5.3 `get_leave_form_data`

用途：

- 获取请假单内容

来源系统：

- OA 的请假业务数据
- 对应对象：`BpmOALeaveDO`

读取内容：

- 请假类型
- 开始时间
- 结束时间
- 时长
- 原因

### 5.4 `get_user_profile`

用途：

- 获取申请人的基础组织信息

来源系统：

- OA 的 `yudao-module-system`

读取内容：

- 用户
- 部门
- 岗位
- 上级

### 5.5 `get_leave_history_summary`

用途：

- 获取申请人近一段时间的请假摘要

来源系统：

- OA 的 `yudao-module-bpm`
- OA 的请假业务数据

读取内容：

- 近 N 次请假摘要
- 总时长
- 高频模式

### 5.6 `execute_leave_task_action`

用途：

- 执行标准审批动作

来源系统：

- OA 的 `yudao-module-bpm`

第一版只允许 3 个动作：

- `approve`
- `reject`
- `return`

第一版不允许：

- 转派
- 委派
- 加签
- 减签
- 抄送
- 撤回

## 6. AgentHub 第一版到底是什么

第一版不要搞成独立复杂中台。

直接在 OA 里新增：

- `yudao-module-agent`

这个模块就是第一版的 AgentHub 控制面。

它只做 6 件事：

### 6.1 `TaskIngress`

职责：

- 接收 OA 页面发起的 AI 任务

### 6.2 `TaskMapper`

职责：

- 把 OA 上下文转成 OpenFang 的标准任务输入

### 6.3 `ToolGateway`

职责：

- 对 OpenFang 暴露受控工具

### 6.4 `PolicyGate`

职责：

- 限制哪些是只读动作
- 限制哪些动作必须人工确认

### 6.5 `TaskProjection`

职责：

- 把 OpenFang TaskRun 状态投影回 OA

### 6.6 `AuditBridge`

职责：

- 记录调用链、建议结果、实际执行动作、异常

第一版 AgentHub 明确不做：

- 新流程引擎
- 新权限中心
- 新知识库系统
- 新聊天系统
- 自动路由多个 Agent

## 7. OpenFang 与 AgentHub 的接口边界

第一版只走 Agent 专用 Facade，不让 OpenFang直接理解 OA 全部接口。

建议暴露 3 类接口：

### 7.1 上下文读取

- `GET /agent-api/leave-approval/context`

内部聚合：

- BPM 流程实例
- BPM 当前任务
- 请假单
- 申请人信息

### 7.2 历史读取

- `GET /agent-api/leave-approval/history`

内部聚合：

- 历史请假摘要
- 历史审批摘要

### 7.3 动作执行

- `POST /agent-api/leave-approval/action`

只允许动作：

- `approve`
- `reject`
- `return`

## 8. OA 第一版具体接哪个场景

不要接“发起流程”。
不要接“管理员看全部流程”。
不要接“流程建模”。

只接一个场景：

`审批人处理请假待办`

也就是说：

- 用户打开待办中的一条请假审批
- 点击 `AI 分析`
- AI 读取这条待办的上下文
- 给出摘要、风险、建议
- 用户如果确认，点击 `采纳建议并执行`

这才是第一版真实场景。

## 9. 第一版谁是任务发起者

这里必须说死。

第一版任务发起者只有一个：

- 当前登录 OA 的审批人

不是：

- 部门
- 系统
- AgentHub
- OpenFang

第一版任务主线是：

> 一个真实审批人，在处理一条真实请假待办时，调用一个固定 Agent。

因此任务上下文必须固定包含：

- `oa_user_id`
- `bpm_task_id`
- `process_instance_id`
- `leave_id`
- `scene_code = leave_approval`
- `agent_code = leave_approval_copilot`

## 10. OpenFang 任务输入格式

第一版不要给模型自由发挥。

任务输入固定成结构化对象。

### 10.1 分析任务

```json
{
  "scene": "leave_approval",
  "oa_user_id": 1001,
  "bpm_task_id": "task_123",
  "process_instance_id": "proc_456",
  "leave_id": 789,
  "requested_action_scope": ["analyze", "suggest"],
  "execution_mode": "human_in_command"
}
```

### 10.2 执行任务

```json
{
  "scene": "leave_approval",
  "oa_user_id": 1001,
  "bpm_task_id": "task_123",
  "process_instance_id": "proc_456",
  "leave_id": 789,
  "requested_action_scope": ["execute"],
  "approved_action": "approve",
  "execution_mode": "on_behalf_of"
}
```

## 11. 第一版执行模式

第一版只保留 2 种：

### 11.1 `human_in_command`

用途：

- AI 只做读取、分析、建议

### 11.2 `on_behalf_of`

用途：

- 审批人明确确认后，AI 代为执行标准动作

第一版不做：

- `autonomous_job`

因为审批场景第一版不需要自治。

## 12. OA 第一版需要新增什么

### 12.1 新模块

- `yudao-module-agent`

### 12.2 新表

第一版只建 4 张表。

#### `agent_scene_binding`

作用：

- 绑定场景到固定 Agent

示例：

- `leave_approval -> leave_approval_copilot`

#### `agent_task`

作用：

- 记录一次 AI 辅助审批任务

关键字段：

- `id`
- `scene_code`
- `oa_user_id`
- `bpm_task_id`
- `process_instance_id`
- `biz_id`
- `openfang_task_run_id`
- `status`
- `suggested_action`
- `final_action`

#### `agent_task_result`

作用：

- 存 AI 分析结果

关键字段：

- `agent_task_id`
- `summary`
- `risk_points_json`
- `suggestion_json`
- `tool_trace_json`

#### `agent_task_audit`

作用：

- 存任务生命周期事件

关键字段：

- `agent_task_id`
- `event_type`
- `payload`
- `operator_type`
- `operator_id`

## 13. OA 第一版页面入口

只做两个地方：

### 13.1 请假审批待办详情页

新增按钮：

- `AI 分析`
- `采纳建议并执行`

### 13.2 AI 任务记录页

展示：

- 发起人
- 对应待办
- AI 摘要
- 风险点
- 建议动作
- 实际执行动作
- 调用轨迹

第一版不要做大而全的 AI 控制台。

## 14. MVP 事件流

第一版完整链路如下：

1. 审批人登录 OA
2. 审批人打开一条请假待办
3. 点击 `AI 分析`
4. `yudao-module-agent` 创建 `agent_task`
5. `TaskMapper` 组装任务输入
6. `OpenFangGateway` 调用 OpenFang 启动 `leave_approval_copilot`
7. OpenFang 依次调用：
   - `get_leave_process_instance`
   - `get_leave_task_detail`
   - `get_leave_form_data`
   - `get_user_profile`
   - `get_leave_history_summary`
8. OpenFang 输出：
   - 摘要
   - 风险点
   - 建议动作
9. `TaskProjection` 回写 OA
10. 审批人在页面上查看结果
11. 如果审批人点击 `采纳建议并执行`
12. `yudao-module-agent` 发起第二个执行任务
13. OpenFang 调用 `execute_leave_task_action`
14. OA BPM 完成标准审批动作
15. 结果回写 `agent_task_result` 和 `agent_task_audit`

## 15. 第一版明确不做什么

- 不做数字部门
- 不做多 Agent 协作
- 不做群聊工作空间
- 不做开放式工具市场
- 不做通用审批动作全集
- 不做跨 CRM / ERP / 商城联动

这些全部往后放。

## 16. 开工顺序

如果现在就开始，按这个顺序执行：

1. 固定场景：`leave_approval`
2. 固定 Agent：`leave_approval_copilot`
3. 固定 3 个 Skills
4. 固定 6 个 Tools
5. 新建 `yudao-module-agent`
6. 建 4 张表
7. 做 3 个 Facade 接口：
   - 上下文读取
   - 历史读取
   - 动作执行
8. 先打通 `AI 分析`
9. 再接 `采纳建议并执行`
10. 最后做任务记录页和审计

## 17. 一句最终定义

第一版不是“OpenFang 接入 OA 平台”。

第一版是：

> 让一个固定 Agent，在一个固定请假审批场景里，调用一组固定 Tools，辅助一个固定审批人完成固定动作。

如果这件事做不清楚，后面所有“数字部门”“组织映射”“AgentHub”都不应该开始。
