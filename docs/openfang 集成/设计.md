# OpenFang 与 OA 集成设计

## 1. 结论

不要把 OpenFang 硬塞进 OA，当成 OA 里的一个“大功能模块”。
也不要让 OA 去主导 Agent Runtime。

正确做法是：

```text
OA = 企业组织与治理真相源
OpenFang = Agent 执行内核
集成层 = 授权、任务、审批、审计、知识同步
```

原因很简单：

- OA 擅长组织、权限、流程、审计、业务对象
- OpenFang 擅长 Agent、Channel、Skill、Task Runtime、Approval Gate、工具执行
- 两套系统都想当老大，边界就会腐烂

本设计的目标不是“在 OA 里加一个聊天机器人”，而是把 OA 升级成“人类员工 + 数字员工”的统一治理面。

## 2. 设计依据

从 OpenFang 当前仓库看，这个方向不是空想，已经有明确基础：

- OpenFang 把自己定义为 Agent OS，而不是聊天框架
- 已有“企业组织 -> 部门 -> Agent 员工 -> 工具”的权限模型草图
- 已有双权限链模型：入口侧权限与工具侧权限取交集
- 已有 TaskRun 一等公民设计，说明它已经接受“长任务、打断、审批、副作用”不能靠聊天记录硬撑
- 已有“群聊式数字部门”设计文档，说明“数字部门 / 数字员工”方向与现有骨架不冲突

因此，本阶段不是从 0 到 1，而是把产品叙事收敛成系统边界。

## 3. 问题定义

目标问题：

- 是否可以在 OA 中引入“AI 部门”或“数字部门”
- 是否可以把 OpenFang 的 Agent 映射为“数字员工”
- 如何保证这种映射在组织、权限、流程、审计上是可控的

答案是：可以，但只能成立一半。

成立的部分：

- 部门
- 岗位
- 员工
- 汇报关系
- 审批链
- 数据权限
- 任务分发

不成立的部分：

- 不能把 Agent 当成 OA 普通用户的一个变体
- 不能让 Agent 直接继承 OA 全部行为语义
- 不能让 OA 成为 Agent Runtime 的编排器

根本原因：

- OA 用户是治理主体
- Agent 是执行主体
- 两者都需要身份，但不是同一种身份

## 4. 核心原则

### 4.1 一个问题只允许一个真相源

建议边界如下：

- OA 负责：
  - 组织架构
  - 人员与岗位
  - 角色权限
  - BPM 审批
  - 业务单据
  - 企业知识主数据
  - 审计归档与经营报表
- OpenFang 负责：
  - Agent 定义与运行
  - Skill / Tool 执行
  - 多 Agent 协作
  - Channel 接入
  - 会话与 Workspace Context
  - TaskRun 状态机
  - Approval Gate 的运行时阻塞
- 集成层负责：
  - 身份映射
  - 能力映射
  - 任务投递
  - 审批回调
  - 事件同步
  - 知识同步或检索代理

### 4.2 审批真相只能有一个

建议：

- 任务真相在 OpenFang
- 审批真相在 OA BPM

如果审批同时做在 OA 和 OpenFang，最终一定出现“双审批真相”。

### 4.3 Agent 必须有独立安全主体

最容易做错的是让 Agent 冒充 OA 普通用户去调企业接口。

正确做法：

- Agent 有独立 `AgentPrincipal`
- 当 Agent 代表某个用户执行时，进入 `On-Behalf-Of` 模式
- 权限取交集，而不是直接继承用户权限

## 5. 双视图模型

建议把“AI 部门”拆成两个视图：

### 5.1 数字组织视图

给 OA 用户看：

- 部门
- 岗位
- AI 员工
- 主管
- 任务
- 待办
- 审批
- 绩效

这是业务建模视图。

### 5.2 Agent Runtime 视图

给 OpenFang 用：

- Department Profile
- Role Agent
- Skill Bundle
- Knowledge Pack
- Task Run
- Approval Request
- Workspace Session

这是执行建模视图。

前者和后者名字可以像，但不要强行共享同一套表。

## 6. 建议的核心对象

先把对象钉死，再谈实现。

### 6.1 `OrgUnit`

OA 的真实部门，例如：

- 销售部
- 财务部
- 法务部

### 6.2 `DigitalDepartment`

一个面向 Agent 协作的业务视图。

特征：

- 可映射到一个或多个 `OrgUnit`
- 不一定等于 OA 行政部门
- 面向用户表达“这是一个数字团队”

### 6.3 `RoleAgent`

数字岗位实例，例如：

- `sales_assistant_agent`
- `approval_secretary_agent`
- `crm_analyst_agent`

### 6.4 `AgentPrincipal`

Agent 的安全主体。

必须具备：

- 独立身份
- 可审计性
- 能力边界
- 可停用与撤权
- 可签名或可验证来源

### 6.5 `KnowledgePack`

该角色长期可读的知识域。

注意：

- 不是全库可见
- 不是简单把 OA 文档库全部暴露给 Agent

### 6.6 `ToolCapability`

Agent 可调用的企业工具集合。

注意：

- 不是权限字符串的简单复制
- 应该是受控工具能力的集合

### 6.7 `TaskRun`

一次具体任务执行。

规则：

- 唯一真相在 OpenFang
- OA 只消费投影，不接管内部状态机

### 6.8 `ApprovalBinding`

OpenFang 审批节点与 OA BPM 实例的绑定关系。

作用：

- 让两边审批对象可关联
- 让审批结果能回流
- 保证审计链闭合

## 7. 推荐的总体架构

```text
用户 / 飞书 / OA 页面
        |
        v
       OA
  (组织/权限/流程/业务)
        |
        v
     集成层
  (身份映射/任务路由/审批绑定/事件同步)
        |
        v
   OpenFang Runtime
 (Agent/Skill/TaskRun/Workspace/Tool Gateway)
        |
        v
 企业受控 API / 知识服务 / 外部渠道
```

架构关键点：

- OA 不直接管 Agent Loop
- OpenFang 不直接写 OA 数据库
- Tool Gateway 不直接碰业务表
- 所有写动作都走企业 API 或受控服务

## 8. 正确的请求链路

建议采用以下链路：

1. 用户在 OA 或飞书中发起请求
2. 请求进入 OA，形成业务任务或协作任务
3. OA 判断是否交给某个 `DigitalDepartment`
4. 集成层调用 OpenFang，创建 `TaskRun`
5. OpenFang 根据角色、Skill、Workspace Context 执行
6. 涉及企业动作时，统一经过 `Tool Gateway`
7. `Tool Gateway` 不直接写 OA 数据，而是调用受控企业 API
8. 高风险动作生成审批请求
9. 审批真相落在 OA BPM
10. OA 将审批结果回推 OpenFang
11. OpenFang 继续、终止或补偿
12. 全链路事件回写 OA，用于审计和经营视图

两个硬约束：

- 任务真相在 OpenFang
- 审批真相在 OA

## 9. 权限模型

权限判定建议采用三层交集：

```text
can_execute =
  agent_policy_allow
  ∧ member_role_allow
  ∧ runtime_guardrails
```

具体解释：

- `agent_policy_allow`
  - 这个 Agent 岗位本身允许做什么
- `member_role_allow`
  - 当前用户、部门、租户、业务角色允许它在此场景下做什么
- `runtime_guardrails`
  - 运行时护栏是否放行，例如审批、风险级别、预算、频控、工具限制

这意味着：

- Agent 从来不应该天然拥有某人的全部权限
- “代表某人执行”必须是显式模式
- 高风险动作必须被运行时护栏再次约束

## 10. 产品壳设计

不建议首页直接做“Agent 聊天大厅”。

更合理的是两层 UI：

### 10.1 OA 侧

业务用户使用：

- 数字组织
- AI 岗位配置
- 授权范围
- 待办与审批
- 审计与绩效

### 10.2 OpenFang 侧

平台运营与研发使用：

- TaskRun 详情
- Workspace Context
- Tool 调用轨迹
- 失败分类
- Runtime 诊断

原则：

- 业务用户看 OA
- 研发和平台运营看 OpenFang
- 不要逼业务用户理解 Runtime

## 11. 反模式

以下设计应明确禁止：

### 11.1 把 Agent 直接做成 OA 用户类型

问题：

- 登录模型污染
- 菜单和会话语义污染
- 审计责任混乱
- 权限撤销困难

### 11.2 让 OpenFang 直连 OA 数据库写表

问题：

- 绕开业务校验
- 绕开审计
- 破坏事务边界
- 未来不可治理

### 11.3 让 OA 理解 OpenFang 内部状态机

问题：

- 边界逆转
- 协议扩散
- 演进困难

OA 只应该消费稳定投影，而不是接管 Runtime 细节。

### 11.4 把业务编排写死进 OpenFang 内核

问题：

- 业务耦合进基础设施
- 通用性被破坏
- 后续很难做多场景

### 11.5 一开始就追求“AI 部门包打天下”

问题：

- 权限范围过大
- 风险难控
- 反馈周期过长

## 12. 第一阶段落地范围

第一阶段不要做“AI 员工自治组织”，先做“OA 驱动的受控执行”。

优先场景：

- 审批助理
- 知识问答助理
- 销售助理
- CRM 清洗助理
- 周报分析助理

统一约束：

- Agent 以只读能力为主
- 写动作必须经过审批或明确授权
- 所有写动作走企业 API，不走数据库
- 所有高风险动作必须可回滚或可补偿

这才是能上线的第一版。

## 13. 演进路径

### 阶段 1：受控单 Agent

目标：

- 一个岗位，一个 Agent
- OA 发任务
- OpenFang 执行
- OA 承接审批与审计

### 阶段 2：部门内多 Agent 协作

目标：

- 引入 `DigitalDepartment`
- 引入 Lead Agent 与 Specialist Agent
- 引入共享 Workspace Context
- 引入任务分发与汇总

### 阶段 3：数字组织治理

目标：

- 岗位模板化
- 权限与知识域模板化
- 绩效与风险可观测
- 多租户可运营

## 14. 最终判断

你真正要做的，不是“在 OA 里加 AI 部门”。

你真正要做的是：

```text
把 OA 从人类组织系统，
升级成“人类员工 + 数字员工”的统一治理面。
```

而 OpenFang 是数字员工的内燃机，不是组织系统本身。

只有在这个前提下，“数字部门 / 数字员工”的映射才会稳定，才不会在权限、审批、审计和运行时边界上烂掉。
