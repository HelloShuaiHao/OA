docs/工作记录/20260322-解决方案.md# 20260322 解决方案（AgentX × OA × OpenFang）

## 1. 目标与硬约束

### 业务目标
- 让企业在 OA 内完成 Agent 的全生命周期管理（创建、授权、发布、监控、审计）。
- 让 Agent 能自动处理可自动化流程，并在需要时可靠拉人介入。
- 支持一个 Agent 绑定多个业务流程场景，并按规则自动路由。

### 硬约束（必须满足）
- 不允许业务用户输入 `workflow_id`、`scenario_code`、JSON 等技术字段。
- 不要求业务用户进入 OpenFang 做配置。
- OA 是治理与审批真相源；OpenFang 是运行时执行引擎。

## 2. 现状复杂点（问题本质）

- 目前“场景到 workflow”的映射暴露了技术心智，业务用户难理解。
- 用户难判断“哪个流程由哪个 Agent 接手”，路由关系不透明。
- 人工介入（谁能介入、何时介入）缺少统一配置入口。
- Channel（如 Telegram）配置与用户身份绑定链路还未产品化。

## 3. 总体方案（产品形态）

## 3.1 OA 成为唯一控制台
- 在 OA 提供 **Agent 管理中心**，OpenFang 隐藏在系统内部。
- OpenFang 仅由平台管理员维护连接，不向业务用户暴露技术参数。

## 3.2 配置分层（把技术字段关进后台）
- 业务层（给业务管理员）：
  - 业务场景名称（如：请假审批助手）
  - 适用流程（从 OA 流程下拉选择）
  - 自动审批策略（如：<=2 天自动通过）
  - 人工介入策略（触发条件、审批角色）
- 平台层（给平台管理员，默认一次配置）：
  - 场景到 OpenFang workflow 映射
  - Tool/Skill 白名单
  - 运行参数与回调策略

## 3.3 三个“自动化翻译器”
- 流程翻译器：`OA流程定义/实例 -> 内部场景键`
- 路由翻译器：`内部场景键 -> OpenFang workflow`
- 身份翻译器：`Channel账号 -> OA用户ID`

> 业务用户只看“中文名与规则”，不看任何 ID。

## 4. 针对 7 个问题的落地解法

## 4.1 Agent 在 OA 创建与管理
- 提供 OA 页面：Agent 列表、启停、版本、负责人、生效范围。
- 发布动作一键完成：OA 下发配置到 OpenFang（用户无感）。

## 4.2 Skill / 权限 / Tool 管理
- OA 中用”能力包”抽象（如：审批查询、审批执行、通知发送）。
- 技术上的 Tool 名称在后台映射，不暴露给业务用户。
- 权限采用”角色 + 能力包 + 数据范围”三维授权。

## 4.3 流程管理（重要更新）

> 详细设计见：[复用现有 Workflow 文档](./20260322-复用现有Workflow.md)

**核心原则：复用 OA 现有的 Flowable 流程管理，不重复造轮子**

### 4.3.1 架构设计

```
┌─────────────────────────────────────────────────┐
│      OA 流程管理（Flowable - 已有）              │
│  - 可视化流程设计器（BPMN 2.0）                  │
│  - 流程定义管理                                  │
│  - 流程实例执行                                  │
│  - 已有的审批、判断、通知等节点                  │
├─────────────────────────────────────────────────┤
│      AgentX 扩展节点（新增）                     │
│  - AI 决策节点                                   │
│  - Tool 调用节点                                 │
│  - 数据查询节点                                  │
│  - 外部 API 调用节点                             │
├─────────────────────────────────────────────────┤
│      AgentX 流程执行引擎（桥接层）               │
│  - 监听 Flowable 流程事件                        │
│  - 执行 AgentX 扩展节点                          │
│  - 调用 OpenFang（复杂 AI 场景，可选）          │
└─────────────────────────────────────────────────┘
```

### 4.3.2 流程创建方式

**方式 A：AI 辅助生成（推荐）**
```
1. 用户输入自然语言描述
2. AI 生成 BPMN XML
3. 自动导入到 Flowable 流程设计器
4. 用户在设计器中查看和调整
5. 保存流程定义
```

**方式 B：使用流程模板**
```
从模板库选择：
- 审批类模板（请假、报销、采购）
- ERP 类模板（库存、订单、对账）
- 数据处理类模板（清洗、报表、同步）
- 客户服务类模板（跟进、投诉、售后）
```

**方式 C：手动设计**
```
使用 Flowable 流程设计器：
- 标准节点（用户任务、网关等）
- AgentX 扩展节点（AI 决策、Tool 调用）
```

### 4.3.3 AgentX 扩展节点

**在 Flowable 流程设计器中新增的节点：**

1. **AI 决策节点**
   - 使用 LLM 进行智能判断
   - 输入：流程变量
   - 输出：决策结果

2. **Tool 调用节点**
   - 调用 AgentX 注册的 Tool
   - 如：查询数据、发送通知、调用 API

3. **数据查询节点**
   - 查询 OA 系统数据
   - 如：查询用户、部门、业务数据

4. **外部 API 节点**
   - 调用外部系统 API
   - 支持 HTTP/REST

### 4.3.4 Agent 与流程的关系

**多对多关系：**
- 一个 Agent 可以关联多个流程
- 一个流程可以被多个 Agent 使用
- Agent 根据任务上下文选择合适的流程

**选择策略：**
- 规则选择：配置明确的匹配规则
- AI 自动选择：LLM 根据上下文判断

### 4.3.5 与 OpenFang 的关系

**重新定位 OpenFang：**

| 场景 | 使用 | 理由 |
|------|------|------|
| 标准审批流程 | Flowable | OA 已有，成熟稳定 |
| 带 AI 决策的流程 | Flowable + AgentX 扩展 | 复用现有基础 |
| 复杂 AI 推理 | OpenFang | 需要强大的 AI 能力 |
| 多 Agent 协作 | OpenFang | Flowable 不支持 |
| 长时间 AI 任务 | OpenFang | 需要状态管理 |

**OpenFang 作为可选增强：**
- 不是必需的
- 用于复杂 AI 场景
- 与 Flowable 互补而非替代

## 4.4 与人的交互定义（修正版）

**核心原则：Workflow 定义规则，OA 提供数据**

- **在 Workflow 中定义审批角色规则**（如：直属上级、部门负责人）
- **OA 提供角色解析服务**（运行时查询”张三的直属上级是李四”）
- **禁止在 OA 配置中硬编码流程逻辑**

**正确的分层：**
```
Workflow（OpenFang）: 定义”当金额>5000时，找申请人的直属上级审批”
OA 角色解析服务: 提供”张三的直属上级 = 李四”
Runtime: 执行时调用 OA API，解析角色到具体用户
```

**Workflow 示例：**
```json
{
  “type”: “wait_for_approval”,
  “approver”: {
    “type”: “role”,
    “role”: “direct_manager”,
    “of”: “${task.applicant_id}”
  },
  “condition”: “${task.amount > 5000}”,
  “timeout”: “24h”
}
```

**OA 提供的角色解析 API：**
```java
interface RoleResolver {
    /**
     * 解析角色到具体用户
     * @param roleType 角色类型（direct_manager, department_head, etc.）
     * @param context 上下文（申请人ID、部门ID等）
     * @return 用户ID列表
     */
    List<Long> resolveRole(String roleType, Map<String, Object> context);
}
```

**为什么这样设计：**
1. Workflow 是自包含的，可以独立测试和复用
2. 同一个 workflow 可以在不同组织结构下运行
3. 流程逻辑和组织数据分离，职责清晰
4. 符合”流程即代码”原则

**特殊情况：固定审批人**
如果某些场景需要固定审批人（如：财务总监），可以在 workflow 中引用固定角色：
```json
{
  “type”: “wait_for_approval”,
  “approver”: {
    “type”: “fixed_role”,
    “role”: “finance_approver”  // OA 配置这个角色对应的具体用户
  }
}
```

## 4.5 无需人工介入场景
- 支持“纯自动模式”：满足规则直接闭环，无人工节点。
- 仍保留审计与可回放，确保事后可追踪。

## 4.6 Channel 接入
- Channel 连接入口统一在 OA（Telegram/企业微信/邮件等）。
- OA 存连接配置，OpenFang 作为执行通道。
- 后续新增渠道时对业务层无心智变化。

## 4.7 谁能和 Agent 交互（身份治理）
- 首次外部交互用户进入“待认证池”。
- 认证后绑定到 OA 用户（员工/外部联系人）。
- OA 用户中心可查看“用户-渠道账号”绑定关系与历史交互。

## 5. 关键数据模型（对业务可见）

- Agent（数字员工）
- 业务场景（中文名）
- 流程绑定（选择 OA 流程）
- 介入策略（条件 + 角色）
- 渠道绑定（账号映射）
- 运行记录（任务、审批、审计）

> `workflow_id / scenario_code / json` 仅保留在平台层，不给业务用户输入。

## 6. 推荐实施顺序（分阶段）

### Phase A（先降复杂度，最快提升体验）
- OA 上线 Agent 管理中心（隐藏技术字段）。
- 场景配置改为“选流程定义 + 选规则”，后台自动映射 workflow。
- 介入策略改为“选角色/人”，不允许手填。

### Phase B（打通身份与渠道）
- Channel 接入配置收口到 OA。
- 上线账号绑定与首次认证流程（外部账号 -> OA 用户）。

### Phase C（规模化运营）
- 模板化：预置常见业务场景（请假/报销/采购）。
- 版本化：Agent 配置灰度发布、回滚、AB 策略。

## 7. 验收标准（面向体验）

- 业务管理员配置流程时，页面不出现任何技术 ID/JSON 输入框。
- 新建 Agent 并绑定“请假审批”场景 <= 3 分钟可完成。
- 用户从提交请假到自动审批/人工介入链路可完整回放。
- 外部渠道用户可被识别并绑定 OA 身份。
- 关键动作（授权、审批、回调）全链路可审计。

### 8.5 用户身份绑定流程

**场景：用户首次在 Telegram 与 Agent 交互（一次性绑定，长期有效）**

**优雅的绑定流程（推荐）：**

1. 用户发送消息给 Bot
2. OpenFang 检测到未绑定用户
3. Bot 回复：
   ```
   您好！检测到您是首次使用，请先绑定企业账号。

   点击下方链接完成绑定：
   https://oa.company.com/agentx/bind?token=ABC123XYZ

   （链接 10 分钟内有效）
   ```

4. 用户点击链接，自动跳转到 OA 登录页
5. 用户登录 OA（如果已登录则跳过）
6. 登录成功后，系统自动完成绑定，显示：
   ```
   ✓ 绑定成功！

   您的 Telegram 账号已与 OA 账号关联
   现在可以返回 Telegram 继续对话
   ```
7. 用户返回 Telegram，发送任意消息，自动识别身份并开始对话

**技术实现：**

```
绑定链接格式：
https://oa.company.com/agentx/bind?token={token}

Token 包含信息（JWT）：
- channel_type: telegram
- channel_user_id: 123456789
- channel_username: @john
- expire_time: 10分钟后（仅限此链接有效期，防止链接泄露）
- signature: 签名防篡改

注意：
- 链接 10 分钟有效：防止链接被截获后长期滥用
- 绑定关系永久有效：一旦绑定成功，长期有效
- 除非用户主动解绑或管理员撤销
```

**后端处理流程：**

```java
@GetMapping("/agentx/bind")
public String bind(@RequestParam String token, HttpSession session) {
    // 1. 验证 token 有效性
    BindToken bindToken = validateToken(token);

    // 2. 检查用户是否已登录
    if (!isUserLoggedIn(session)) {
        // 未登录，跳转到登录页，登录后回调此接口
        return "redirect:/login?redirect=/agentx/bind?token=" + token;
    }

    // 3. 获取当前登录用户
    Long userId = getCurrentUserId(session);

    // 4. 创建绑定记录
    createBinding(userId, bindToken.getChannelType(),
                  bindToken.getChannelUserId(),
                  bindToken.getChannelUsername());

    // 5. 通知 OpenFang 绑定成功
    notifyOpenFang(bindToken.getChannelUserId(), userId);

    // 6. 显示成功页面
    return "bind-success";
}
```

- 后续所有对话自动识别身份，**无需重复绑定**
- 除非用户主动解绑或管理员撤销绑定

**绑定管理：**
- 用户可在 OA 个人中心查看已绑定的渠道账号
- 支持解绑和重新绑定
- 管理员可在用户管理中查看和管理所有绑定关系
- 支持一个 OA 账号绑定多个社交账号（Telegram + 企业微信 + 钉钉）

## 10. 最终结论

当前方向是正确的：`OA管治理 + OpenFang管运行 + AgentX做桥接`。
下一步的重点不是继续堆功能，而是 **把技术概念彻底从业务界面下沉**，把”能跑”升级为”好用、可推广、可规模化运营”。

**核心改进点：**
1. 用户配置时完全不接触技术 ID 和 JSON
2. 通过向导式界面和模板降低配置门槛
3. 后台自动生成和维护 workflow 映射
4. 统一的渠道和身份管理入口
5. 可视化的任务监控和审计
