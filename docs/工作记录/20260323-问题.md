# 2026-03-23 Agent 访问控制与认证集成设计固化

## 1. 问题定义

这件事不是单纯的“给 Bot 加一个绑定链接”，而是一个三方协同问题，至少涉及：

1. OA 创建 Agent 时，要定义这个 Agent 的访问范围
2. Agent 发布到 OpenFang 并绑定某个 channel bot 后，实际用户请求先到 OpenFang
3. 只有在 OpenFang 判断“需要绑定”时，才进入 OA 身份绑定与认证集成

因此，设计必须把下面三层拆开：

- Agent 访问策略定义层
- OpenFang 运行时执行门禁层
- OA 身份绑定层

---

## 2. 三方职责边界

### 2.1 OA 的职责

OA 是**策略源头**与**身份权威源**，负责：

- 创建 Agent
- 定义 Agent 的访问策略
- 定义 Agent 允许访问的人群范围
- 保存 channel 与 agent 的关联关系
- 保存渠道用户与 OA 用户的绑定关系
- 在 OpenFang 需要时，返回访问判定结果和绑定链接

OA 不应该直接承担所有消息入口处理，因为真实消息先到 OpenFang。

### 2.2 OpenFang 的职责

OpenFang 是**消息入口**和**运行时执行者**，负责：

- 接收 Telegram / WeCom / DingTalk 等 channel 消息
- 识别当前消息属于哪个 channel、哪个外部用户、哪个 agent
- 在执行 agent 能力前，先向 OA 询问访问策略
- 严格遵守 OA 返回的准入结果
- 对未放行请求不给能力执行，只返回绑定引导或拒绝提示

OpenFang 不能自行猜测权限，也不能绕过 OA 的策略直接放行。

### 2.3 外部渠道用户的职责

外部用户只负责发起请求与完成绑定动作：

- 给 bot 发消息
- 如果需要绑定，则点击链接并登录 OA
- 绑定后再次与 bot 交互

---

## 3. 统一设计目标

系统最终要支持两类 Agent：

### 3.1 公开型 Agent

例如：

- 销售助手
- 展会接待助手
- 产品咨询助手

特点：

- 外部用户可以直接对话
- 不要求先绑定 OA 身份
- 可以匿名访问
- 但能力范围通常受限，不能访问内部数据、审批、组织信息

### 3.2 内部型 Agent

例如：

- 请假审批助手
- 财务查询助手
- HR 助手
- 内部 IT 服务台

特点：

- 必须先绑定 OA 身份
- 只有绑定且在授权范围内的用户才可调用
- 可以进一步限制为“所有员工 / 指定部门 / 指定人员”

---

## 4. 核心设计原则

### 4.1 访问控制优先于能力执行

任何消息进入 OpenFang 后，在触发 Agent 能力前，必须先做访问控制判定。

顺序必须是：

1. 识别目标 Agent
2. 获取 Agent 访问策略
3. 判断是否需要绑定
4. 若需要绑定，则判断当前 channel 用户是否已绑定
5. 若已绑定，则继续判断该 OA 用户是否在允许范围内
6. 只有全部通过，才能真正执行 Agent 能力

### 4.2 Agent 的访问策略独立于 channel

同一个 Agent 可以同时挂在多个 channel 上，但其业务属性不应该因为 channel 改变。

因此策略分两层：

- Agent 级：这个 Agent 是公开型还是内部型
- Channel 级：这个 channel 上允许哪些用户群体访问该 Agent

如果一个 channel 绑定了多个 agent，则每个 agent 都需要自己的认证模式。

### 4.3 OA 是唯一可信策略源

OpenFang 不维护访问控制真值，不在本地长期缓存最终权限结论。

OpenFang 可以做短时缓存以减少调用量，但策略真值始终以 OA 为准。

---

## 5. 统一访问模型

### 5.1 Agent 认证模式

每个 Agent 在每个 channel 上需要有一个 `authMode`：

- `public`
  - 允许匿名访问
  - 不要求 OA 绑定
- `bind_required`
  - 必须绑定 OA 身份后才可访问

默认值必须是：

- `bind_required`

原因：

- 对内部 Agent 更安全
- 避免新建 Agent 因漏配置而被外部直接访问

### 5.2 访问范围

当 `authMode = bind_required` 时，还需要进一步校验绑定后的 OA 用户是否属于允许范围。

建议统一支持：

- `all`
  - 所有内部员工可访问
- `dept`
  - 仅指定部门员工可访问
- `user`
  - 仅指定人员可访问

这里的“访问范围”是 OA 侧组织权限判断，不是 OpenFang 本地概念。

### 5.3 访问判定结果

OpenFang 向 OA 查询后，只接受三类结果：

#### 结果 A：允许匿名访问

- `accessGranted = true`
- `authRequired = false`

OpenFang 可以直接执行 Agent 能力。

#### 结果 B：必须绑定，但当前未绑定

- `accessGranted = false`
- `authRequired = true`
- `bound = false`
- 返回 `bindUrl`

OpenFang 不执行 Agent 能力，只回复绑定引导。

#### 结果 C：已绑定且在允许范围内

- `accessGranted = true`
- `authRequired = true`
- `bound = true`

OpenFang 允许继续执行。

#### 结果 D：已绑定但不在授权范围内

- `accessGranted = false`
- `authRequired = true`
- `bound = true`

OpenFang 不执行能力，只返回“无权限访问该 Agent”。

## 6. 三段式完整链路

## 6.1 第一段：OA 创建 Agent 时定义访问策略

在 OA 创建 Agent 或配置 channel-agent 关系时，需要明确以下信息：

- Agent 基本信息
- Agent 同步到 OpenFang 的标识
- channel 绑定关系
- 每个 agent 在该 channel 上的 `authMode`
- 若需要认证，则绑定后的访问范围

这里的关键是：

- “公开 / 必须绑定”不是 channel 全局属性
- 而是 `channel + agent` 维度上的策略

原因：

- 同一个 Telegram bot 未来可能路由多个 agent
- 其中有的 agent 可以公开，有的 agent 必须内部员工才能用

### 现阶段建议

短期可以先存在 OA 的 channel 配置 JSON 中；
长期更合理的是独立成明确的数据模型，而不是埋在 `config` JSON 里。

---

## 6.2 第二段：用户请求先到 OpenFang，由 OpenFang 执行门禁

这是整个设计里最关键的一段。

真实运行时顺序如下：

1. 用户给 bot 发消息
2. OpenFang 识别：
   - `channelType`
   - `channelUserId`
   - 目标 `agent`
3. OpenFang 调用 OA 的访问评估接口
4. OA 返回该用户对该 Agent 的准入结论
5. OpenFang 根据结果决定：
   - 放行执行
   - 返回绑定链接
   - 返回无权限提示

这一步说明：

- “是否需要认证”必须由 OF 在运行时执行
- 不是 OA 页面上配置完就算完成
- 只要 OF 不执行门禁，所有策略都只是静态配置

### OpenFang 必须遵守的约束

- 未拿到 OA 明确放行结果前，不得执行 Agent 能力
- 不得绕过 OA 本地写死“公开 / 内部”规则
- 不得把“已绑定”误判为“有权限”
- 必须在绑定后继续检查部门/人员范围

## 6.3 第三段：需要认证时才进入 OA 身份绑定

OA 身份绑定只是第三层，不是第一层。

它只解决：

- 这个渠道用户是谁
- 这个渠道用户映射到哪个 OA 用户

它并不单独决定“是否能使用某个 Agent”。

因为即使已绑定，也可能：

- 不在 Agent 允许的部门里
- 不在 Agent 允许的人员名单里
- 没有资格调用这个内部 Agent

因此正确关系是：

- 绑定成功 != 一定可访问 Agent
- 绑定成功只是访问内部 Agent 的必要条件之一

## 7. 推荐接口契约

为了支持 OF 运行时门禁，OA 至少要提供一个统一的访问评估接口。

### 7.1 推荐接口

`POST /admin-api/agentx/channel/access/evaluate`

请求建议包含：

- `channelType`
- `channelUserId`
- `channelUsername`
- `agentId` 或 `agentKey`

响应建议包含：

- `accessGranted`
- `authRequired`
- `bound`
- `authMode`
- `accessControlType`
- `bindUrl`
- `message`

### 7.2 接口语义

这个接口不负责真正执行 Agent；
只负责告诉 OF：

- 这个请求该不该放行
- 如果不放行，是因为未绑定还是未授权
- 如果未绑定，应该给用户哪个链接

- OA 侧绑定能力已完成
- OF 运行时准入门禁仍需闭环验证

## 9. 最终固化结论

这件事必须按照下面的架构理解：

1. **OA 定策略**
   - 创建 Agent 时定义公开或内部
   - 定义允许访问的人群范围

2. **OF 执行策略**
   - 所有 channel 消息先进入 OF
   - OF 先问 OA 能不能放行
   - OF 必须遵守 OA 的结果

3. **OA 做身份映射**
   - 只有在需要认证时，才引导用户绑定 OA
   - 绑定后仍要继续做权限范围判断

因此，真正的目标不是“首条消息触发绑定”，而是：

**OF 在每次能力执行前，都能正确理解并执行 OA 下发的 Agent 访问策略。**
