# 服务感知与配置同步设计

## 1. 问题定义

在 OA 与 OpenFang 集成的架构中，需要解决以下核心问题：

- OA 如何发现和管理 OpenFang 实例
- OpenFang 如何感知 OA 的配置变更
- 多租户 SaaS 场景下的实例隔离
- 配置变更的实时同步与版本管理

## 2. 服务发现模型

### 2.1 单租户场景（Phase 1）

**架构**：
```
OA (单实例) ←→ OpenFang (单实例)
```

**发现方式**：
- 静态配置：OA 配置文件中指定 OpenFang 的 endpoint
- 健康检查：OA 定期 ping OpenFang 的 `/health` 端点

**配置示例**：
```yaml
# application-agentx.yml
agentx:
  openfang:
    endpoint: "http://localhost:4201"
    api-key: "${OPENFANG_API_KEY}"
    health-check-interval: 30s
    timeout: 10s
```

### 2.2 多租户 SaaS 场景（Phase 2+）

**架构选型**：

**方案 A：共享 OpenFang 实例**
```
OA (多租户)
  ├─ 租户 A ─┐
  ├─ 租户 B ─┼─→ OpenFang (共享实例，租户隔离)
  └─ 租户 C ─┘
```

优点：
- 资源利用率高
- 运维成本低
- 统一升级

缺点：
- 需要严格的租户隔离
- 性能相互影响
- 安全边界复杂

**方案 B：独立 OpenFang 实例**
```
OA (多租户)
  ├─ 租户 A ──→ OpenFang A
  ├─ 租户 B ──→ OpenFang B
  └─ 租户 C ──→ OpenFang C
```

优点：
- 完全隔离
- 独立扩缩容
- 故障隔离

缺点：
- 资源成本高
- 运维复杂度高

**推荐方案**：混合模式
- 小租户共享实例（方案 A）
- 大租户独立实例（方案 B）
- 根据租户规模和 SLA 动态分配

### 2.3 服务注册表设计

**数据模型**：
```sql
CREATE TABLE agentx_openfang_instance (
    id BIGINT PRIMARY KEY,
    tenant_id BIGINT NOT NULL COMMENT '租户 ID，0 表示共享实例',
    instance_id VARCHAR(64) NOT NULL COMMENT 'OpenFang 实例唯一标识',
    endpoint VARCHAR(255) NOT NULL COMMENT 'API 端点',
    api_key_encrypted VARCHAR(512) COMMENT '加密的 API Key',
    status TINYINT NOT NULL COMMENT '0=离线 1=在线 2=维护中',
    version VARCHAR(32) COMMENT 'OpenFang 版本',
    capacity_config JSON COMMENT '容量配置：max_agents, max_concurrent_tasks',
    last_heartbeat DATETIME COMMENT '最后心跳时间',
    created_time DATETIME NOT NULL,
    updated_time DATETIME NOT NULL,
    INDEX idx_tenant (tenant_id),
    UNIQUE KEY uk_instance (instance_id)
) COMMENT 'OpenFang 实例注册表';
```

## 3. 配置同步机制

### 3.1 配置分类

**OA → OpenFang 的配置**：
- Agent 定义（角色、能力、知识域）
- Tool 授权（哪些 Agent 可以调用哪些 Tool）
- 审批策略（哪些操作需要审批）
- 租户配额（并发任务数、存储限制）

**OpenFang → OA 的配置**：
- Agent 运行状态
- Tool 调用统计
- 错误与告警
- 资源使用情况

### 3.2 同步模式

**推模式（Push）**：
- OA 配置变更后，主动推送到 OpenFang
- 适用于：Agent 定义、授权变更、紧急策略更新

**拉模式（Pull）**：
- OpenFang 定期从 OA 拉取配置
- 适用于：知识库更新、非紧急配置

**事件驱动（Event）**：
- OA 发布配置变更事件
- OpenFang 订阅并处理
- 适用于：实时性要求高的场景

**推荐策略**：
- 核心配置（Agent、授权）：推模式 + 版本校验
- 知识库：拉模式 + 增量同步
- 紧急策略：事件驱动 + 推模式双保险

### 3.3 配置版本管理

**版本模型**：
```java
public class AgentConfigVersion {
    private Long tenantId;
    private String agentId;
    private Long version;          // 单调递增
    private String configHash;     // 配置内容 SHA256
    private LocalDateTime syncedAt;
    private SyncStatus status;     // PENDING, SYNCED, FAILED
}
```

**同步流程**：
```
1. OA 更新 Agent 配置
2. 生成新版本号 version++
3. 计算配置 hash
4. 调用 OpenFang API: PUT /api/agents/{agentId}/config
   - Headers: X-Config-Version: {version}
   - Body: 完整配置
5. OpenFang 验证版本号（必须 > 当前版本）
6. OpenFang 应用配置并返回确认
7. OA 更新同步状态为 SYNCED
```

**冲突处理**：
- 如果 OpenFang 返回版本冲突，OA 重新拉取当前版本
- 如果网络失败，OA 标记为 PENDING，后台重试
- 最大重试 3 次，失败后告警

## 4. 健康检查与故障恢复

### 4.1 健康检查

**OA 侧检查**：
```java
@Scheduled(fixedDelay = 30000) // 30 秒
public void checkOpenFangHealth() {
    for (OpenFangInstance instance : instanceRegistry.getAll()) {
        try {
            HealthResponse health = openFangClient.health(instance);
            if (health.isHealthy()) {
                instance.updateStatus(ONLINE);
                instance.updateHeartbeat(now());
            } else {
                instance.updateStatus(DEGRADED);
                alertService.warn("OpenFang 实例降级", instance);
            }
        } catch (Exception e) {
            instance.updateStatus(OFFLINE);
            alertService.error("OpenFang 实例离线", instance, e);
        }
    }
}
```

**OpenFang 健康端点**：
```
GET /api/health

Response:
{
  "status": "healthy",
  "version": "0.3.0",
  "uptime_seconds": 86400,
  "active_agents": 5,
  "running_tasks": 12,
  "resource_usage": {
    "cpu_percent": 45.2,
    "memory_mb": 2048,
    "disk_mb": 10240
  }
}
```

### 4.2 故障恢复

**场景 1：OpenFang 短暂离线**
- OA 将新任务放入本地队列
- OpenFang 恢复后，OA 重新投递
- 超时时间：5 分钟

**场景 2：OpenFang 长时间离线**
- OA 标记任务为失败
- 通知用户服务不可用
- 运维介入处理

**场景 3：配置同步失败**
- OA 保留配置变更记录
- 后台定期重试
- 如果 OpenFang 恢复，自动补齐配置

## 5. 租户隔离设计

### 5.1 租户标识传递

**所有 OA → OpenFang 的请求必须携带租户标识**：
```
POST /api/tasks
Headers:
  X-Tenant-ID: 1001
  X-User-ID: 2001
  Authorization: Bearer {token}
```

**OpenFang 验证**：
- 检查 token 是否属于该租户
- 检查用户是否属于该租户
- 拒绝跨租户访问

### 5.2 数据隔离

**OpenFang 内部隔离**：
- Agent 配置按租户隔离
- TaskRun 按租户隔离
- Memory/Knowledge 按租户隔离
- 审计日志按租户隔离

**存储隔离**：
```
/data
  /tenant_1001
    /agents
    /tasks
    /memory
  /tenant_1002
    /agents
    /tasks
    /memory
```

### 5.3 资源配额

**配额模型**：
```sql
CREATE TABLE agentx_tenant_quota (
    tenant_id BIGINT PRIMARY KEY,
    max_agents INT NOT NULL DEFAULT 10,
    max_concurrent_tasks INT NOT NULL DEFAULT 50,
    max_storage_mb INT NOT NULL DEFAULT 10240,
    max_tool_calls_per_day INT NOT NULL DEFAULT 10000,
    created_time DATETIME NOT NULL,
    updated_time DATETIME NOT NULL
) COMMENT '租户配额';
```

**配额检查**：
- OA 在创建 Agent 前检查配额
- OA 在投递任务前检查配额
- OpenFang 在执行 Tool 时检查配额
- 超配额时拒绝请求并返回明确错误

**创建/更新 Agent**：
```
PUT /api/tenants/{tenantId}/agents/{agentId}
Headers:
  X-Config-Version: 5
  Authorization: Bearer {token}

Request:
{
  "name": "审批助手",
  "role": "approval_assistant",
```

## 7. 实施建议

### Phase 1：单租户静态配置
- OA 配置文件指定 OpenFang endpoint
- 手动配置 Agent
- 基础健康检查

### Phase 2：动态配置同步
- 实现配置同步 API
- 版本管理
- 自动重试

### Phase 3：多租户支持
- 租户隔离
- 配额管理
- 实例路由

### Phase 4：高可用
- 多实例负载均衡
- 故障自动切换
- 配置热更新

## 8. 安全考虑

- API Key 加密存储
- 租户间严格隔离
- 配置变更审计
- 敏感配置脱敏
- HTTPS 强制
