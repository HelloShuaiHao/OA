  员工和 OA/OpenFang 的交互，不能只放在 OA，也不能只放在 OpenFang。
  正确拆法是：

  - OA 管“这个外部账号是谁的、是否允许绑定、绑定后能代表什么身份”
  - OpenFang 管“WhatsApp / Telegram 连接器、Webhook、会话、消息路由、Agent 执行”
  - 集成层管“把某条外部消息解析成哪个员工、哪个数字员工、什么权限上下文”

  这和你们现在文档里的主边界其实一致：OA = 治理真相源，设计.md:10；OpenFang 负责 Channel 接入，设计.md:82；集成层负责身份映射和任务投递，总体架构设计.md:129。

  你现在缺的不是“再选一边”，而是补一个单独模型：

  1. OA 新增“员工外部联系身份”模型
     字段至少要有：employee_id、channel_type、external_account_id、binding_status、verified_at、can_login、can_delegate_to_agent、data_scope_policy。
     这表示“这个 Telegram/WhatsApp 账号归谁、被允许干什么”。
  2. OpenFang 保留“渠道连接实例”模型
     比如 channel_connection、channel_session、message_thread、agent_endpoint。
     它只管收发消息，不做员工主数据真相。
  3. 集成层新增“路由绑定”模型
     比如 employee_channel_binding + agent_channel_route。
     前者解决“这个社交账号是谁”，后者解决“这个人发到这个渠道时，默认接哪个 Agent/场景”。

  这样以后员工体验会很清楚：

  - 员工在 OA 里完成社交账号绑定和授权
  - OA 下发绑定结果给集成层 / OpenFang
  - 员工从 WhatsApp/Telegram 发消息
  - OpenFang 收到消息后，先查“外部账号 -> 员工身份 -> 可用 Agent/权限”
  - 再进入对应场景执行

  你要避免两个典型错误：

  - 不要让员工直接去 OpenFang 里各自绑社交账号
    问题是身份归属、离职回收、审计、权限会失控。
  - 不要让 OA 自己去接 WhatsApp/Telegram webhook
    问题是 OA 会被迫长成聊天运行时，边界会烂掉。

  所以更准确地说，不是“员工社交媒体绑定应该在 OA 上吧”，而是：

  绑定治理 应该在 OA 上。
  渠道接入与会话运行 应该在 OpenFang 上。
  身份解析与权限路由 应该在集成层。
