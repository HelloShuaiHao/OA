• 一个审批请求过来，按现在这份方案，人话就是这样：

  1. AI 先干活，跑在 OpenFang 里。
     它执行任务时，如果遇到高风险动作，比如“替用户提交请假单”“修改业务单据”“触发外部写操作”，不会直接干，而是先把任务卡住，生成一个“待审批 gate”。
     这时候：

  - OpenFang 里会记住这个任务正在等审批
  - 它会给这个审批一个 approval_id
  - 任务上会挂一个 pending_approval_ids

  2. OA 发现这个任务卡住了。
     OA 通过 GET /api/tasks/{id} 看到这个任务当前在等审批，并拿到 pending_approval_ids。
  3. OA 还不能直接审批，因为 GET /api/tasks/{id} 只有“有审批在等”，没有完整审批单内容。
     所以 OA 还要再拿审批详情：

  - 要么 OpenFang 提供“按 approval_id 查详情”的接口
  - 要么 AgentX 在中间提前把审批详情缓存好了

  审批详情里要有这些：

  - 标题
  - 原因
  - 风险等级
  - 这次准备做什么动作
  - 关联哪个任务、哪个业务单据

  4. OA 用这份详情在自己的 BPM 里建审批单。
     这一步之后，人类就正式介入了。
     也就是：

  - AI 不直接找人点“同意/拒绝”
  - 而是 OA 把它翻译成企业自己的审批流程
  - 审批人、审批链、抄送、留痕，都走 OA 现有 BPM

  5. 人类审批。
     审批人只在 OA 里操作：

  - 同意
  - 拒绝

  OA 是审批决议的唯一真相源。
  也就是说，“到底批没批”这件事，以 OA BPM 为准。

  6. OA 把结果回写给 OpenFang。
     如果审批通过，OA 调 OpenFang 的 approve 接口；
     如果审批拒绝，OA 调 reject 接口。
  7. OpenFang 收到结果后继续处理任务。

  - 批准：解除阻塞，AI 继续往下执行
  - 拒绝：停止、回退或补偿，按任务语义处理

  所以职责分得很清楚：

  - AI / OpenFang：
    负责发现“这一步不能自己做”，把任务挂起，等待审批，再根据结果继续执行
  - OA：
    负责把这个等待审批翻译成正式审批单
  - 人类审批人：
    只在 OA 里做决定
  - 最终审批结果真相：
    在 OA，不在 OpenFang
  - 任务为什么卡住、卡在哪、恢复后怎么继续：
    在 OpenFang

  一句话总结：

  AI 负责“申请批准再执行”，人类负责“在 OA 里做决定”，OA 负责“保存审批真相”，OpenFang 负责“保存任务阻塞和恢复状态”。

› 1. AI 先干活，跑在 OpenFang 里。
       它执行任务时，如果遇到高风险动作，比如“替用户提交请假单”“修改业务单据”“触发外部写操作”，不会直接干，而是先把任务卡住，生成一个“待审批 gate”。
       这时候：

    - OpenFang 里会记住这个任务正在等审批
    - 它会给这个审批一个 approval_id  这些是在哪里定义的，未来有两种设置方式，一种是作为流程写入流程里，看哪一步 ai 可以自主决定，另外一种就是给 agent 的 skill 说明了，你觉得怎么样?


• 这些东西本质上有三层定义，别混在一起：

  1. 运行时层定义
     这是 OpenFang 自己的真相对象。
     这里定义的是：

  - task_run_id
  - 当前任务状态
  - pending_approval_ids
  - approval_id
  - 当前为什么被卡住
  - 批准后恢复哪一步，拒绝后怎么终止/补偿

  也就是说，approval_id 不是 OA 定义的，是 OpenFang 运行时在“触发审批 gate”那一刻生成的。它首先属于运行时对象，不属于 BPM 单号。

  2. 策略层定义
     这是“什么情况下必须审批”的规则。
     这个才是你问的重点。未来确实可以有两种来源：

  - 流程里显式配置
    例子：第 3 步“创建请假单”必须审批，第 5 步“发送通知”可自动执行。
  - Skill / Tool 的能力说明里配置
    例子：某个 skill 或 tool 被标成 requires_approval、risk_level=high、auto_execute=false。

  3. 集成层定义
     这是 OA 和 OpenFang 之间怎么对接。
     这里定义的是：

  - OpenFang 的 approval_id 怎么映射到 OA BPM 审批单
  - OA 审批通过/拒绝后，怎么回写给 OpenFang

  我的判断很直接：

  两种方式都要有，但优先级必须明确，不能让它们互相打架。

  比较合理的设计是：

  - Skill / Tool 层负责定义“能力的固有风险”
    也就是默认规则。
    例如：
      - 读用户资料：低风险
      - 提交业务单据：高风险
      - 调外部支付接口：必须审批
  - 流程层负责定义“场景里的具体收紧或放宽”
    也就是场景覆盖。
    例如：
      - 同样是“创建请假单”
      - 在“普通员工请假”流程里必须审批
      - 在“AI 生成请假草稿”流程里只允许生成草稿，不允许直接提交

  所以不要做成二选一，应该做成：

  最终审批要求 = Skill/Tool 默认风险规则 + 流程场景覆盖规则

  更具体一点：

  - Skill/Tool 定义基础能力边界
    适合定义“这个动作天生危险不危险”
  - 流程定义当前业务上下文里的执行边界
    适合定义“在这个场景里放不放权给 AI”

  我不建议只靠 skill 文档说明，原因很简单：

  - 文档容易漂
  - 不够结构化
  - 运行时不好稳定执行
  - 后面审计也不好追

  我也不建议只靠流程硬编码，原因也一样：

  - 同一个危险动作会在很多流程里重复配置
  - 容易漏
  - 基础安全边界会散掉

  更稳的落法是：

  - Tool/Skill 元数据里有结构化字段
      - risk_level
      - approval_required
      - approval_scope
      - allowed_without_approval
  - 流程节点里有覆盖字段
      - approval_mode = inherit | force_required | force_skip
      - approval_policy_ref
      - max_autonomy_level

  然后运行时判定：

  - 先看 Tool/Skill 默认规则
  - 再看流程节点是否覆盖
  - 最后生成 approval_id 和 gate

  一句话结论：

  approval_id 和等待审批状态，定义在 OpenFang 运行时。
  “什么时候要审批”，建议同时支持“Skill/Tool 默认规则”和“流程节点覆盖规则”，但必须以结构化配置实现，不能只靠 skill 文字说明。

  如果你愿意，我下一步可以直接给你画一份最实用的模型：

  - Tool/Skill 怎么定义审批字段
  - 流程节点怎么覆盖
  - 运行时怎么生成 approval_id
  - OA 怎么接 BPM 单
