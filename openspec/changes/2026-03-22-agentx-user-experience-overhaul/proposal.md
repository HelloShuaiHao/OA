# AgentX 用户体验全面改造

**提案日期：** 2026-03-22
**状态：** Draft
**负责人：** AgentX Team
**预计工期：** 10-13 周（分 3 个 Phase）

---

## 1. 背景与问题

### 1.1 当前问题

AgentX 系统已完成技术验证，8 层架构实现完整，31 个单元测试全部通过。但存在严重的**用户体验问题**：

1. **配置复杂度高**
   - 用户需要输入 `workflow_id`、`scenario_code`、JSON 等技术字段
   - 需要在多个系统（OA、OpenFang）之间切换配置
   - 场景到 workflow 的映射关系不透明

2. **流程管理重复**
   - 当前设计想重新做一套 Workflow 管理
   - 与 OA 现有的 Flowable 流程管理功能重复
   - 浪费开发资源，增加系统复杂度

3. **身份绑定缺失**
   - 外部渠道（Telegram）用户无法绑定到 OA 账号
   - 缺少统一的身份治理机制

4. **运维能力不足**
   - 缺少监控告警
   - 故障排查困难
   - 性能瓶颈不可见

### 1.2 业务影响

- **推广受阻**：配置门槛高，业务管理员难以上手
- **维护成本高**：重复造轮子，增加维护负担
- **用户体验差**：技术细节暴露，不符合产品化标准

### 1.3 解决方案核心思路

**基于文档：** `docs/工作记录/20260322-解决方案.md`

1. **隐藏技术复杂度**：业务用户不接触任何技术 ID/JSON
2. **复用现有基础**：使用 OA 的 Flowable，不重复造轮子
3. **分阶段实施**：Phase A/B/C 逐步推进，风险可控
4. **用户体验优先**：5 步向导，3 分钟创建 Agent

## 2. 目标与硬约束

### 2.1 业务目标

- 让企业在 OA 内完成 Agent 的全生命周期管理
- 让 Agent 能自动处理可自动化流程，并在需要时可靠拉人介入
- 支持一个 Agent 绑定多个业务流程场景，并按规则自动路由

### 2.2 硬约束（必须满足）

- ✅ 不允许业务用户输入 `workflow_id`、`scenario_code`、JSON 等技术字段
- ✅ 不要求业务用户进入 OpenFang 做配置
- ✅ OA 是治理与审批真相源；OpenFang 是运行时执行引擎
- ✅ 复用 OA 现有的 Flowable 流程管理，不重复造轮子

### 2.3 验收标准（面向体验）

- 业务管理员配置流程时，页面不出现任何技术 ID/JSON 输入框
- 新建 Agent 并绑定"请假审批"场景 <= 3 分钟可完成
- 用户从提交请假到自动审批/人工介入链路可完整回放
- 外部渠道用户可被识别并绑定 OA 身份
- 关键动作（授权、审批、回调）全链路可审计

## 3. 架构设计

### 3.1 三层架构

```
┌─────────────────────────────────────────────────┐
│      OA 流程管理（Flowable - 已有）              │
│  - 可视化流程设计器（BPMN 2.0）                  │
│  - 流程定义管理                                  │
│  - 已有的审批、判断、通知等节点                  │
├─────────────────────────────────────────────────┤
│      AgentX 扩展节点（新增）                     │
│  - AI 决策节点                                   │
│  - Tool 调用节点                                 │
│  - 数据查询节点                                  │
│  - 外部 API 调用节点                             │
├─────────────────────────────────────────────────┤
│      AgentX 流程执行引擎（桥接层）               │
│  - 监听 Flowable 流程事件                        │
│  - 执行 AgentX 扩展节点                          │
│  - 调用 OpenFang（复杂 AI 场景，可选）          │
└─────────────────────────────────────────────────┘
```

### 3.2 核心设计原则

1. **复用 Flowable**：不重新开发 Workflow 引擎
2. **Workflow 定义规则，OA 提供数据**：职责分离
3. **OpenFang 可选增强**：简单场景用 Flowable，复杂场景用 OpenFang
4. **数字员工是一等公民**：在组织架构中可见，可加入部门

## 5. 风险与缓解

### 5.1 技术风险

| 风险 | 严重程度 | 缓解措施 |
|------|---------|---------|
| Flowable 扩展节点开发复杂度超预期 | 高 | 先做 POC 验证（1 周） |
| OpenFang 可用性问题 | 中 | 实现熔断降级 |
| 自然语言生成 BPMN 准确率低 | 中 | Phase A 不实现，使用模板库 |

### 5.2 业务风险

| 风险 | 严重程度 | 缓解措施 |
|------|---------|---------|
| 用户接受度低 | 高 | 充分的用户测试，迭代优化 |
| 配置门槛仍然过高 | 中 | 提供完善的模板和向导 |

## 6. 资源需求

### 6.1 人力资源

- **最小配置（1 人）：** 10-13 周
- **推荐配置（2 人）：** 5-7 周
- **理想配置（3 人）：** 4-5 周

### 6.2 技术栈

- 后端：Spring Boot + Flowable + MyBatis Plus
- 前端：Vue 3 + Element Plus
- 数据库：MySQL + Redis
- 消息队列：RabbitMQ（Phase C）

## 7. 成功指标

- 用户配置时间从 30 分钟降至 3 分钟
- 技术细节完全隐藏，业务用户友好
- 系统可用性 > 99%
- 关键操作响应时间 < 3 秒
